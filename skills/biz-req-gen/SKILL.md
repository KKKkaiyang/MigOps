# MigOps 业务需求生成（biz-req-gen）

本技能沉淀「从一段文本诉求 → 一份独立需求文档 → 合并进平台总 BRD」的标准流程。目标是让每一次零散需求都能**独立存档、可追溯**，同时**不破坏**总文档的全景视图与统一编号。

所有规范以仓库 `CODEBUDDY.md`（库表命名 §3 / 命名规范 §4 / 前后端分层 §5 / 设计令牌 §6.4）与本目录 `templates/fragment-requirement.md` 模板为权威来源。

适用场景：
- 用户贴入一段业务描述（功能点、优化点、新模块诉求），说「帮我记一下需求 / 写个需求文档」。
- 需要将零散需求整理成可评审、可交付的正式需求文档。
- 需求可能与既有功能（b01~b07）冲突或边界不清，需要边生成边与用户确认。

**不适用**：后端/前端代码实现、数据库 DDL 落地——本技能只产出**需求文档**，不写代码。

---

## 1. 核心原则（不可偏离）

1. **碎片化文档独立成篇**：每一份需求（或一个紧密关联的需求簇）落到 `docs/业务需求/` 下的**单独** `.md` 文件，文件名 `<模块域>-<主题>需求.md`。总文档不替代它，仅引用与整合。
2. **总文档负责全景与仲裁**：`迁移管家平台-完整需求文档.md` 是「整合版」，只做全景视图、交叉仲裁与统一编号；详细内容以碎片原文为准。合并时必须**增量更新**索引表、模块章节、决策与修订记录，**不得覆盖**既有内容。
3. **先读后写，冲突必确认**：生成前必须先读相关碎片文档与总文档对应章节，识别冲突/歧义，用 `AskUserQuestion` 交互确认后再落盘。
4. **沿用既有模板与风格**：文档结构、表格形式、编号风格对齐既有碎片文档（参考 `用户与空间管理-功能优化需求.md`）；语义配色、术语、状态机、权限模型引用 `CODEBUDDY.md` 与总文档，不重复造概念。
5. **需求编号带模块前缀**：碎片化文档内需求编号用 `<模块前缀>-<序号>`（如 `UR-01`、`SP-02`、`R1`）；合并进总文档时保持原文编号，总文档仅做全局章节编排。

---

## 2. 输入与输出

- **输入（用户提供）**：一段文本诉求（自由描述，可含页面/操作/角色/边界等信息）。若信息过稀，先用 `AskUserQuestion` 补齐关键项（见 §4）。
- **输出**：
  1. `docs/业务需求/<模块域>-<主题>需求.md`（新建，独立碎片文档，含「已确认决策汇总」「修订记录」）。
  2. 对 `docs/业务需求/迁移管家平台-完整需求文档.md` 的**增量合并**（见 §6）。
  3. 一份「本次生成摘要」回给用户：文件名、归属模块、关键决策、与既有需求的冲突处理结果。

---

## 3. 模块域与命名约定

### 3.1 模块前缀映射（用于文件命名与冲突检测）
| 前缀 | 模块域（文件命名用） | 对应总文档章节 |
| --- | --- | --- |
| `common_` / `b01_` | 用户与空间管理 / 项目空间管理 | §4 公共业务、§5.0 空间视图框架 |
| `b02_` | 项目资料 | §5.1 项目资料索引 |
| `b03_` | 数据迁移 | §5.2 数据迁移管理 |
| `b04_` | 任务迁移（含标签 b06 概念 / 自定义台账） | §5.3 任务迁移管理 |
| `b05_` | 数据校验 | 二期（§10.2） |
| `b07_` | 血缘管理 | §5.4 血缘管理 |
| `b99_` | 统计分析 | 二期（§10.2） |

> 命名尽量与既有文件风格一致，如 `用户与空间管理-功能优化需求.md`、`任务迁移-任务台账需求.md`、`血缘管理-数据血缘需求.md`。一个需求若跨模块，以**主模块**命名，跨模块影响在正文与总文档中分别落位。

### 3.2 文件命名
- 格式：`<模块域>-<主题>需求.md`，主题用短横线分隔的简洁中文，避免空格。
- 若同名文件已存在：不要覆盖。先判断是「同一需求的迭代/补充」还是「新需求」，用 `AskUserQuestion` 让用户选择：**追加到原文档** / **另起新文档（加后缀如 `-补充需求`）**。

## 4. 工作流程

### 步骤 0 · 接收需求文本
- 若用户尚未贴入描述，提示：「请描述你的业务诉求（可包含：想做什么功能、涉及哪些页面/操作、哪些角色、有什么边界或约束）。」不要臆造需求。
- 若描述过稀（例如只有一句话且无任何上下文），先用 `AskUserQuestion` 补齐以下关键项（按需，不全问）：
  - 归属模块 / 页面位置（如「b04 任务台账列表」）；
  - 目标角色（L0/L1/L2 或「全部」）；
  - 优先级（P0/P1/P2，默认 P1）；
  - 是否复用既有接口/能力，还是全新。

### 步骤 1 · 分析与归类（必须先读）
- 用 Read / Grep 读取：
  - `docs/业务需求/` 下**同模块**的既有碎片文档；
  - `迁移管家平台-完整需求文档.md` 的**对应章节**（§1 索引、§3 信息架构、§5.x 模块章节、§7 接口全景、§9 决策汇总）；
  - 根目录 `CODEBUDDY.md`（§3 库表命名、§3.3 审计字段/逻辑删除、§6.4 设计令牌、§8 评审结论）。
- 输出分析结论（内部）：归属模块域、主题、涉及前端/后端/库、初步优先级、可能冲突点列表。

### 步骤 2 · 冲突与歧义检测（关键）
遍历以下冲突维度，逐项标记「无冲突 / 疑似冲突 / 歧义不清」：
- **功能/入口重复**：是否与既有需求定义了同一入口、按钮、字段（如总文档已定义「进入项目」入口）？
- **API 路径 / 库表前缀冲突**：是否新增了与既有重复或矛盾的接口路径、表名前缀、状态枚举取值？
- **角色权限矛盾**：操作的可执行角色是否与总文档 §3.2 角色权限总览或 §4.4 空间权限冲突？
- **状态机/枚举矛盾**：状态流转、取值是否与既有约定不一致（如默认逻辑删除 vs 物理删除特例）？
- **视觉/交互偏离**：是否偏离 `CODEBUDDY.md` §6.4 设计令牌（主色、圆角、危险语义等）？
- **边界不清**：描述中缺少判定条件、范围、异常处理等（如「删除后编码能否复用」类问题）。

任何「疑似冲突」或「歧义不清」项 → **必须进入步骤 3 交互确认**，禁止自行臆断覆盖。

### 步骤 3 · 交互式确认（AskUserQuestion）
- 将步骤 2 检出的冲突/歧义，**逐组**用 `AskUserQuestion` 呈现给用户，给出推荐选项（推荐项置首、标注「推荐」），例如：
  - 冲突类型：「新需求与《任务迁移-任务台账需求 §3.1》已定义的『台账入口』重复」 → 选项：覆盖原定义 / 扩展原需求（追加到原文档）/ 并存（新文档，明确区分场景）/ 调整方案。
  - 歧义项：「删除后空间编码是否允许复用？」 → 选项：不允许复用（默认）/ 允许复用（需放宽唯一约束）。
- 可一次问多个独立问题（每个问题 options 2~4 项），multiSelect 仅当需多选时开启。
- 把用户决策**记录为决策项**（编号 D1/D2… 或沿用既有决策编号风格），用于碎片文档「§已确认决策汇总」与总文档 §9。
- 若无任何冲突/歧义，跳过本步并明确告知用户「未发现冲突，直接进入生成」。

### 步骤 4 · 生成碎片化需求文档
- 复制 `templates/fragment-requirement.md` 作为骨架，按分析结果填充。
- 头部 `适用范围` 写好；`配套文档` 链接指向 `CODEBUDDY.md`、相关源文档（如有）、总 BRD。
- 正文含：概述（背景/范围/术语）、需求总览表、逐条功能设计（描述/交互界面/权限/接口）、非功能性约束、验收标准表、**已确认决策汇总**（含步骤 3 的全部决策）、修订记录。
- 需求编号带模块前缀；若与既有需求补充/扩展，用 §9「补充需求」式小节沿用既有文档结构。
- 文件名遵循 §3.2。写完后 Read 自检结构完整。

### 步骤 5 · 增量合并进总文档
按 §6 执行。核心是**只增不改**：新增来源行、新增/扩展章节、新增决策小节、新增修订记录；若发现需对既有内容做**修正（非新增）**，先用 AskUserQuestion 与用户确认仲裁口径，再动笔。

### 步骤 6 · 交付摘要
向用户回执（简洁）：
- 新建碎片文档路径；
- 归属模块、核心需求编号与优先级；
- 步骤 3 中确认的决策（D1…）；
- 对总文档做了哪些增量更新（哪些表/章节/小节）；
- 若因信息不足主动做了合理假设，一并列出「待你复核」项。

## 5. 自检清单（交付前）

- [ ] 已 Read 同模块碎片文档与总文档对应章节（步骤 1 不可省）。
- [ ] 步骤 2 全部冲突维度已评估，疑似冲突/歧义均经 `AskUserQuestion` 确认（步骤 3）。
- [ ] 碎片文档结构对齐 `templates/fragment-requirement.md`：含概述/总览/功能设计/验收/决策/修订。
- [ ] 文件名符合 `<模块域>-<主题>需求.md`；未覆盖既有同名文件（除非用户选择追加）。
- [ ] 需求编号带模块前缀，术语/状态机/权限引用既有约定，未造新概念。
- [ ] 总文档仅做增量更新：§1.1 来源表、§1.2 模块状态（如需）、相关 §5.x 章节、§9 决策小节、§11 修订记录均已同步；总文档版本号与日期已 bump。
- [ ] 视觉/交互描述未偏离 `CODEBUDDY.md` §6.4。

## 6. 合并进「迁移管家平台-完整需求文档.md」细则

> 总文档结构（截至 V1.0）：§1 文档说明（1.1 来源表 / 1.2 模块总览 / 1.3 术语）、§2 平台概述、§3 信息架构与导航、§4 公共业务、§5 空间内业务（5.0~5.4）、§6 数据模型全景、§7 接口全景、§8 安全质量、§9 已确认决策汇总、§10 范围边界、§11 修订记录。

增量更新清单（按需在对应位置插入，**保持既有编号风格连续**）：

1. **§1.1 整合范围与来源**：在来源文档表格**追加一行**
   `| {文档短名} | V1.0 | {YYYY-MM-DD} | 确认版 | §{新章节号} |`
   若本次为「补充/作废」性质，状态列注明（如 `补充版` / `已作废（留档）`），并视情况在 §10.3 留档。
2. **§1.2 模块总览与状态**：若新需求改变了某模块的本期状态或新增子能力，在「说明」列补充（如新增「XXX 能力」），不改动既有 ✅/⏳ 结论除非用户确认。
3. **§1.3 术语表**：仅当引入新术语时追加，复用既有术语不重复。
4. **§5.x 对应模块章节**：在所属模块小节下**新增子节**（如 §5.3.x），或将内容**并入**既有子节（扩展而非覆盖）。若总文档尚无对应模块章节（如全新的 b0x），在 §5 末尾新增小节并同步更新 §1.1 映射。
5. **§6 / §7（如涉及）**：仅当新增库表 / 接口时，在对应子节追加条目；未涉及则跳过。
6. **§9 已确认决策汇总**：**新增一个小节** `### 9.x {主题}（来源：{文档短名} V1.0）`，列出本次决策（D1…）。不要改动既有 9.1~9.5 内容。
7. **§11 修订记录**：追加一行，记录本次合并；并将文档头部「文档版本」bump（如 V1.0 → V1.1）与「编写日期」更新为当天。
8. **回链**：总文档内的新小节如引用碎片文档细节，用相对链接指向 `./{文档短名}.md`，保持「详情以原件为准」原则。

> 若 `迁移管家平台-完整需求文档.md` 不存在：先告知用户，按 `templates/` + 既有碎片文档结构初始化一份总文档（§1~§11 骨架），再执行合并；或建议先 `git log` 确认是否误删。
