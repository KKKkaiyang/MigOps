## 1. 概述

### 1.1 背景与目标
ak/sk（AccessKey/SecretKey）密钥对当前在《skill 管理》需求中被定义为 skill（b08）的「子功能」（SK-05），用于 skill 的 REST API 上传 / 下载。但随着平台演进，**后续「skill 人机对话方式」需要调用数据迁移（b03）、任务迁移（b04）等接口，自动补录迁移过程记录、更新任务状态 / 台账**——这说明 ak/sk 不应只是 b08 的专属鉴权手段，而应成为**平台通用的公共业务能力**。

本需求目标：
1. **能力归属上移**：将 ak/sk 从 b08 子功能提升为「公共业务通用能力」，明确其服务范围覆盖 b03~b08；
2. **接口开放**：规定 b03/b04/b05/b06/b07/b08 全部接口均支持「登录态（Bearer）**或** ak/sk 签名」双鉴权，复用既有 HMAC 方案（SK-06）；
3. **空间授权明确**：作为空间隔离业务，经 ak/sk 调用时沿用空间成员 / 角色校验，保证安全不越权。

> 注：前端自助入口仍保留在「个人中心 → API 密钥」，本需求**不新建**「公共业务管理」菜单；所谓「整体移植」在本文档中等同于**能力归属与适用范围的上移与平台化**，而非前端入口搬迁（D1）。

### 1.2 范围
- **涉及前端**：无新增页面 / 菜单；ak/sk 自助入口维持「个人中心 → API 密钥」。本需求仅在文档层面完成能力归属与适用范围界定。
- **涉及后端**：将 `get_actor`（Bearer 或 ak/sk 签名统一鉴权，已在 b08 落地）扩展到 b03/b04/b07 全部接口（现有多使用 `get_current_user` 仅 Bearer，需替换）；b08 已完成；b05 二期实现时直接采用 `get_actor`；b06 标签随 b04 一并覆盖。复用既有 `common_user_api_key` 表与 HMAC-SHA256 方案（SK-06），**不新增鉴权协议**。
- **涉及库**：公共库 `mig_common_db`（`common_user_api_key` 表结构不变）。

### 1.3 术语
| 术语 | 含义 |
| --- | --- |
| ak/sk | AccessKey / SecretKey 密钥对，用于 REST API 的 HMAC 签名鉴权 |
| `get_actor` | 统一鉴权依赖：自动判定 `Authorization: Bearer <token>` 或 `X-Access-Key` 等签名头，返回当前操作人（CommonUser） |
| 双鉴权 | 同一接口同时接受「网页登录态」与「ak/sk 签名」两种调用方式 |
| 空间成员校验 | 空间内业务（b03/b04/b05/b06/b07）调用须携带空间上下文，且操作人为该空间成员且具对应角色权限 |

## 3. AK-01 ak/sk 通用能力化

### 3.1 功能描述
将 ak/sk 密钥能力从「skill（b08）子功能」提升为**平台级公共业务通用能力**。明确：ak/sk 不仅服务 b08 的上传 / 下载，也作为 b03/b04/b05/b06/b07 各业务 REST 调用的统一鉴权方式。

前端自助入口维持「个人中心 → API 密钥」（D1），**不在顶部导航或模块区新建「公共业务管理」菜单**；即能力归属上移、前端入口不变。

### 3.2 与既有 D2 的关系（冲突消解）
BRD §9.9 的 **D2 维持不变**：ak/sk 仍由「个人中心 → API 密钥」自助管理，每用户自管自身密钥，不依赖 L0（有意偏离 §3.2 用户管理规则）。

本需求**仅扩展 D2 的适用范围**：由「仅 b08」扩展为「b03~b08 全平台接口」。原《skill 管理》文档 SK-05 中「ak/sk 属于 skill 子功能」的归属表述，以本需求为准——ak/sk 归**公共业务通用能力**。

### 3.3 权限与可用性
- 仍仅本人可管理自身密钥（后端按 `user_id` 过滤，禁止跨用户）。
- 密钥生成 / 列表 / 吊销 / 启用停用四类接口不变，详见 BRD §7.6 `api-keys` 四项。

### 3.4 数据 / 接口（无变更）
- 表 `common_user_api_key`（`mig_common_db`）结构不变：`id` / `user_id` / `access_key`(唯一) / `secret_key_enc`(加密) / `status` / `last_used_at` + 审计字段。
- 接口（不变）：
```
POST   /api/v1/common/users/me/api-keys        # 生成（返回 access_key + secret_key，secret 仅此一次明文）
GET    /api/v1/common/users/me/api-keys        # 列表（secret 掩码）
DELETE /api/v1/common/users/me/api-keys/{id}   # 吊销（逻辑删除）
PATCH  /api/v1/common/users/me/api-keys/{id}   # 启用 / 停用
鉴权：登录态（仅本人）
```

## 4. AK-02 b03~b08 接口支持 ak/sk 调用

### 4.1 功能描述
将下列模块的全部接口，由「仅登录态（Bearer）」扩展为「登录态 **或** ak/sk HMAC 签名」双鉴权，统一通过 `get_actor` 依赖实现（已在 b08 落地验证）：

- **b03** 数据迁移管理；**b04** 任务迁移管理（含概念 `b06` 标签、`b04_saved_view` 自定义台账）；**b07** 血缘管理；
- **b08** skill 管理（已完成）；
- **b05** 数据校验管理（⏳ 二期，实现时直接采用 `get_actor`）；
- `b06` 标签作为 b04 的 UI 概念，随 b04 一并覆盖。

### 4.2 鉴权方案（复用 SK-06，不新增协议）
- **请求头**：`X-Access-Key`、`X-Timestamp`（毫秒）、`X-Nonce`、`X-Signature`。
- **待签字符串** = `HTTP方法 + "\n" + 请求路径 + "\n" + timestamp + "\n" + nonce`（与 SK-06 一致；无 body 不参与）。
- **签名** = `HMAC-SHA256(secret_key, 待签字符串)` 十六进制。
- **服务端校验**：access_key 存在且启用；时间戳偏差 ≤ 5 分钟（防重放）；nonce 5 分钟内不重复；签名一致。任一不通过返回 `40100`。
- 校验通过后的操作人 = 该 ak/sk 对应的用户（`actor = key.user`）。

### 4.3 空间授权模型（D2）
b03/b04/b05/b06/b07 均为**空间隔离业务**（空间库）。经 ak/sk 调用时：
- 调用须携带空间上下文（如 `space_id` / `space_code` 路径或参数）；
- `actor`（密钥持有用户）**须为目标空间的成员且具对应角色权限**，否则后端拒绝（`40300`），与网页端空间权限校验完全一致；
- 不引入「服务账号绑定」等放宽机制（D2 选 A），确保空间隔离不被 ak/sk 绕过。

### 4.4 实施说明（后端改造指引，非新增功能）
- 现有 b03/b04/b07 接口多使用 `get_current_user`（仅 Bearer），需统一替换为 `get_actor`；依赖内部已能区分 Bearer 与签名两种来源。
- 改造对既有网页端（Bearer）**完全兼容**，不影响现有登录态调用。
- b08 已落地 `get_actor`，可作改造样板。

### 4.5 接口清单影响（对应 BRD §7）
- §7.3 b03、§7.4 b04（含标签 / 台账）、§7.5 b07：各接口「鉴权」由「登录态」扩展为「登录态 或 ak/sk 签名」双鉴权。
- §7.6 b08：已含 ak/sk 签名列，无需改动。
- §10.2 b05（二期）：规划接口即采用双鉴权。

## 5. AK-03 skill 经 ak/sk 更新台账（前置能力 / 场景说明）

### 5.1 目标场景
后续「skill 人机对话方式」可持 ak/sk 调用 b03/b04 接口，自动完成：
- 向 `b03_tables/{id}/records` 补录迁移过程记录；
- 更新 `b04_tasks/{id}/status` 任务状态流转、维护 `b04_saved_views` 自定义台账；
实现「skill 驱动的数据 / 任务迁移台账自动化更新」，无需人工在网页逐项操作。

### 5.2 权限前提（依赖 D2）
- 该 ak/sk 的持有用户，须**先由 L0/L1 加入目标迁移空间**并授予相应角色（L1/L2）成为成员；否则调用被拒（`40300`）。
- 建议 skill 使用方在「个人中心 → API 密钥」为执行账号生成 ak/sk，并由空间管理员完成空间授权。

### 5.3 审计与追溯
- 经 ak/sk 的写操作，审计字段 `created_by / updated_by` 记为**密钥持有用户**；
- 日志 / 审计需标识调用来源为 ak/sk（记录 `access_key` 尾号），便于事后追溯，且不打印 `secret_key` 明文、不打印文件内容（沿用 §8 安全约束）。

## 6. 非功能性约束

### 6.1 统一响应与分层（沿用 CODEBUDDY.md §5）
- 接口统一返回 `{ code, message, data, trace_id }`；分页 `{ list, total, page, page_size }`。
- 后端按 router → service → repository → model 分层；跨层用 Pydantic Schema，禁止直接返回 ORM 对象。

### 6.2 安全与质量（沿用 §8）
- `secret_key` 加密存储、仅生成时展示一次；HMAC 签名防重放（时间戳 + nonce）。
- **空间隔离**：b03~b07 调用强制按 `space_id` 过滤，禁止跨空间访问（§8.4）。
- 日志脱敏：禁止打印 `secret_key` 明文、文件内容；审计覆盖经 ak/sk 的写操作。
- 双鉴权对现有 Bearer 调用完全兼容，无回归风险。

### 6.3 界面视觉（沿用 CODEBUDDY.md §6.4）
- 本需求无新增前端页面，不引入第二套配色 / 圆角 / 阴影令牌。
