# 迁移管家（MigOps）公共业务需求 — 用户权限与项目空间管理

> 文档版本：V1.1 ｜ 编写日期：2026-10-21 ｜ 状态：需求确认版（待评审）
> 适用范围：公共业务模块（`mig_common_db`），覆盖用户、角色、权限与项目空间（`b01`）的基础管理体系
> 配套文档：根目录 [`CODEBUDDY.md`](../../CODEBUDDY.md)（开发规范）、`docs/业务需求/迁移管家平台-业务需求文档.html`（平台总 BRD）

## 1. 概述

### 1.1 背景与目标
迁移管家平台以「迁移空间」为隔离单元，将大数据迁移全流程（需求调研 → 元数据/数据迁移 → 任务迁移 → 数据校验 → 客户验收）标准化、线上化。本需求定义平台的**公共业务基座**：

- **用户与认证**：平台所有功能均需登录后访问，统一的账号体系与密码安全策略。
- **角色与权限**：以三级角色（L0/L1/L2）实现「系统级 → 空间级」的权限隔离。
- **项目空间**：作为一切业务数据的隔离单元，空间创建时即完成业务模块表的初始化。

### 1.2 范围
- **归属库**：本需求的数据模型统一归属公共业务库 `mig_common_db`，表名使用 `common_` 前缀（见 `CODEBUDDY.md` §3.2）。
- **与 `b01` 模块的关系**：项目空间管理即 `b01` 模块；空间内的成员关系、角色绑定及 `b02~b05` 业务表存放于各空间库 `mig_<space_code>_db`。
- **不在本需求范围**：`b02~b05` 各业务模块的具体功能（资料、数据迁移、任务迁移、数据校验），仅在「空间创建时初始化」环节被引用。

### 1.3 术语
| 术语 | 含义 |
| --- | --- |
| 用户归属（org_type） | 用户来源标签，仅用于分类展示，不参与权限计算 |
| 全局角色 | 不绑定具体空间、作用于整个平台的角色（仅 L0） |
| 空间角色 | 绑定到具体项目空间、仅在该空间内生效的角色（L1/L2） |
| 项目空间（Space） | 迁移业务的隔离单元，对应独立数据库 `mig_<space_code>_db` |

## 2. 用户模型

### 2.1 用户表（`common_user`）
| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT | PK，自增 | 用户 ID |
| `username` | VARCHAR | 唯一、非空 | 登录用户名 |
| `password` | VARCHAR | 非空 | 密码密文（bcrypt/argon2 哈希，见 §3.2） |
| `name` | VARCHAR | 非空 | 姓名 |
| `email` | VARCHAR | 可空 | 邮箱（预留，自助能力扩展用） |
| `phone` | VARCHAR | 可空 | 手机号（预留） |
| `org_type` | ENUM | 非空 | 用户归属：**内部 / 其他厂商 / 客户 / 腾讯**（仅标签，无权限差异） |
| `status` | ENUM | 非空 | 账号状态：**启用 / 停用**（注销 = 停用，见 §4.2） |
| `login_fail_count` | INT | 默认 0 | 连续登录失败计数（用于验证码/锁定触发） |
| `locked_until` | DATETIME | 可空 | 账号锁定截止时间（NULL 表示未锁定） |
| `last_fail_at` | DATETIME | 可空 | 最近一次登录失败时间 |
| `created_by` / `created_at` | — | 必填 | 审计字段（`CODEBUDDY.md` §3.3） |
| `updated_by` / `updated_at` | — | 必填 | 审计字段 |
| `deleted_at` | DATETIME | 可空 | 逻辑删除标记（NULL 表示未删） |

> 说明：`org_type` 四个取值为并列互斥的标签，仅用于人员分类统计与展示，不参与任何功能权限判断。

### 2.2 默认账户
系统初始化时创建默认账户：
- 用户名：`admin`
- 初始密码：`Admin@1234`
- 角色：L0 系统管理员（全局）
- 状态：启用

## 3. 认证与登录

### 3.1 登录态要求
平台**所有功能**均需通过「用户名 + 密码」登录后方可访问；未登录用户统一跳转至登录页。

### 3.2 密码存储与校验
- 采用 **bcrypt / argon2** 等自适应成本哈希算法存储与校验密码，数据库**仅保存哈希密文，不保存明文**。
- 弃用需求初稿中的「用户名 + 密码 + 指定密钥 SHA256」方案（原文方案盐值可预测、抗暴力破解弱），改用每用户随机盐（由哈希算法内置）的标准方案。
- 校验时由算法直接比对密文，不还原明文。

### 3.3 登录失败处理（验证码 + 锁定）
| 阶段 | 触发条件 | 行为 |
| --- | --- | --- |
| 验证码 | 同一账号**连续 3 次**密码错误 | 后续登录需输入图形验证码 |
| 验证码规则 | 验证码出现后 | 4 位字符，每位从「数字 + 字母」集合随机生成，**排除易混字符 `1`、`I`、`0`、`O`** |
| 账号锁定 | 累计失败达阈值（默认 **10 次**） | 账号锁定 **30 分钟**（`locked_until` 设定期限），锁定期间禁止登录 |
| 计数重置 | 登录成功 | `login_fail_count` 清零、`locked_until` 置空 |

> 说明：验证码仅作人机校验，其输入错误不单独累计失败次数；锁定阈值与锁定时长（10 次 / 30 分钟）为当前默认参数，可在运维配置中调整。

## 4. 用户管理

> 权限约束：**用户管理功能仅 L0 系统管理员可操作**（创建、注销、重置、角色修改）。

### 4.1 用户创建
- 由 L0 管理员创建用户，填写用户名、姓名、归属（`org_type`）、初始密码（或系统生成）。
- 用户名全局唯一；密码需满足 §7 复杂度策略。

### 4.2 用户注销（停用）
- 注销采用**停用**语义：将 `status` 置为「停用」，账号立即不可登录、撤销全部权限。
- **不删除**用户记录与历史操作数据，保留审计完整性；可由 L0 管理员重新「启用」恢复。
- 被停用用户已绑定的空间角色关系保留（停用即等效于无权限），恢复后自动生效。

### 4.3 用户密码重置
- 采用**管理员重置**流程：L0 管理员为用户生成临时密码，用户下次登录时使用临时密码进入，并**强制要求修改**为新密码后方可继续使用。
- 重置后的临时密码同样需满足 §7 复杂度策略。

### 4.4 用户角色修改
- 由 L0 管理员调整用户角色（见 §5）：授予/撤销全局 L0，或在指定空间内授予/撤销 L1、L2。
- 角色变更实时生效，并记录操作审计（操作人、时间、变更前后）。

## 5. 角色与权限模型

### 5.1 角色定义与分配结构
| 角色 | 等级 | 分配范围 | 说明 |
| --- | --- | --- | --- |
| **L0 系统管理员** | 最高 | **全局**（不绑定空间） | 拥有平台全部功能权限，含用户管理；无需逐项授权 |
| **L1 项目管理员** | 中 | **按项目空间**分配 | 在所绑定空间内可创建/管理空间、添加成员 |
| **L2 项目成员** | 低 | **按项目空间**分配 | 在所绑定空间内拥有业务操作全部权限 |

- 权限等级：**L0 > L1 > L2**。
- **同一用户可在不同空间拥有不同空间角色**（如：在空间 A 为 L1、在空间 B 为 L2）。
- L0 全局角色与空间角色可并存：具备 L0 的用户天然拥有所有空间的等效最高权限，同时其空间角色关系仍可被记录。

### 5.2 用户-角色绑定表（`common_user_role`）
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | PK |
| `user_id` | BIGINT | 关联 `common_user.id` |
| `role_level` | ENUM | `L0` / `L1` / `L2` |
| `space_id` | BIGINT | 关联 `b01_space.id`；**L0 行为 NULL（全局）**，L1/L2 必填 |
| 审计字段 | — | `created_by` / `created_at` 等 |

> 唯一约束：`(user_id, role_level, space_id)`（L0 以 `space_id IS NULL` 去重）。

### 5.3 权限矩阵
| 能力 | L0 系统管理员 | L1 项目管理员 | L2 项目成员 |
| --- | --- | --- | --- |
| 全部功能访问 | ✅ | 仅所属空间内 | 仅所属空间内 |
| 用户管理（创建/注销/重置/角色） | ✅ | ❌ | ❌ |
| 创建项目空间 | ✅ | ✅ | ❌ |
| 向空间添加 / 管理成员 | ✅ | ✅（仅本空间） | ❌ |
| 修改空间状态 | ✅（全部空间） | ✅（仅本空间） | ❌ |
| 空间内业务操作（b02~b05） | ✅ | ✅ | ✅（全部） |

> 说明：原文「项目成员拥有所属空间全部权限」与「仅管理员/项目管理员可改状态」存在张力，本需求明确：**L2 拥有所属空间内业务操作（b02~b05）的全部权限，但空间状态修改与成员/角色管理由 L0/L1 负责**。

## 6. 项目空间管理（`b01` 模块）

### 6.1 项目空间主表（`b01_space`，存于 `mig_common_db`）
| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT | PK | 项目 ID（space_id） |
| `space_name` | VARCHAR | 唯一、非空 | 项目名称 |
| `space_code` | VARCHAR | 唯一、非空 | 项目简称（英文字母，用于派生库名） |
| `status` | ENUM | 非空 | 空间状态（见 §6.4） |
| `description` | VARCHAR | 可空 | 项目空间说明 |
| `db_name` | VARCHAR | 非空 | 绑定数据库名，固定为 `mig_<space_code>_db` |
| 审计字段 | — | 必填 | `created_by` / `created_at` / `updated_by` / `updated_at` / `deleted_at` |

> 命名说明（V1.1 修订）：空间主表位于公共库 `mig_common_db`，但表名采用 `b01_` 前缀而非 `common_` 前缀——空间管理属 `b01` 业务模块（`CODEBUDDY.md` §3.2），且与后端代码实现（`code/backend/app/models/space.py`，表名 `b01_space`）保持一致。原 V1.0 文稿中的 `common_space` 表述以此为准则修订。

- `space_code` 约束：仅含小写英文字母与数字，建议正则 `^[a-z][a-z0-9_]{1,30}$`，确保可安全用作数据库名（避免超 MySQL 库名长度限制）。
- `space_name` 与 `space_code` 均**不可重复**。

### 6.2 项目空间创建
1. 按 §6.1 模型创建空间记录，校验 `space_name`、`space_code` 唯一性。
2. 创建对应的业务数据库 `mig_<space_code>_db`。
3. **按业务模块初始化数据表**（每个模块的建表在对应空间库下维护）：
   - `b01_`：空间成员关系、空间角色绑定表（空间级）
   - `b02_`：项目资料管理表
   - `b03_`：数据迁移管理表
   - `b04_`：任务迁移管理表
   - `b05_`：数据校验管理表
4. 初始状态为「初始化」；创建人记为 `created_by`。

### 6.3 项目空间详情
1. 列表查看：用户仅可查看**其权限范围内的项目空间**（L0 看全部；L1/L2 看其被加入的空间）。
2. 状态修改：**仅 L0 系统管理员、L1 项目管理员**可修改空间状态。

### 6.4 空间状态机
```
初始化 ──▶ 交付中 ──▶ 已验收
```
| 状态 | 含义 |
| --- | --- |
| 初始化 | 空间刚创建，业务表已就绪，尚未启动交付 |
| 交付中 | 迁移交付进行中 |
| 已验收 | 客户验收完成（终态） |

> 说明：原文「项目验收」在本需求中规范为终态 **「已验收」**；如需保留「项目验收」字面，可在评审时调整。

## 7. 安全与质量约束

### 7.1 密码复杂度策略
- 长度 ≥ 8 位；至少包含「大写字母、小写字母、数字、特殊字符」中的三类。
- 初始账户 `admin / Admin@1234` 已满足该策略；重置/创建密码均需校验。

### 7.2 审计要求
- 所有业务表遵循 `CODEBUDDY.md` §3.3 审计字段约定（`created_by` / `created_at` / `updated_by` / `updated_at` / `deleted_at`）。
- 敏感操作（用户管理、角色变更、空间状态流转）必须记录操作人、时间、变更前后。
- **禁止**在日志/响应中打印明文密码或密码哈希以外的敏感字段。

### 7.3 统一响应与分层
- 接口遵循 `CODEBUDDY.md` §5.3 统一响应结构 `{ code, message, data, trace_id }`。
- 后端按 router → service → repository → model 分层；跨层用 Pydantic Schema 传递，禁止直接返回 ORM 对象。
